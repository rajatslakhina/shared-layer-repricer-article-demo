Shopify Went Native. I Priced the Same Call Across 12 Features — Eight of Them Never Flip.

Coding agents really did collapse the cost of porting a React Native screen into Swift. They did nothing to the cost of proving two implementations still agree — and that second number is the one your migration business case is missing.

Everyone read Shopify's 10 September post as "React Native lost."

Read the last section instead. After 12 weeks, a 23% faster iOS cold start and 109 MB off the Android binary, the standing principle the team writes down is that "Android and iOS must be at feature parity at all times. React Native enforced this through a shared codebase, and now that we're building natively we'll continue to enforce this through our development and release process."

That single sentence converts a structural guarantee into a recurring process obligation, and the post is honest enough to say so out loud.

It is worth noticing what did get tooling. For the migration itself — old app against new app — Shopify extended their debugging tool, Tardis, so it could snapshot both builds at matching points in a flow and hand an agent the two sets to compare, down to individual analytics payload fields. Proving two implementations agreed was a hard enough problem once that it earned a purpose-built comparison harness.

The standing iOS-versus-Android version of that same question gets a sentence about process. It runs forever.

The cost curve moved. It did not move uniformly.

The post is specific about where the confidence came from. Before committing to anything, one engineer spent a week pointing agents at the React Native app and seeing how much of it they could rebuild in SwiftUI — a proof of concept, explicitly not production-ready, ahead of the real build by a core group of six engineers. And the sentence that matters for anyone copying this play: "agents were particularly effective when they had an existing implementation to work from."

That is a claim about porting, not building. The second platform stopped costing roughly what the first one did. It says nothing about keeping the two honest afterwards.

Two terms, behaving differently under agent assistance: authoring shrinks, verification doesn't. Everyone is repricing the first and nobody the second — which is how you approve a migration on a number that quietly omits the biggest thing agent assistance never made cheaper.

I wanted to know how much that omission is worth, so I wrote the model down as a Swift package and ran it.

Four numbers per feature

A feature gets four inputs. Nothing else about the shared-versus-native argument survives contact with a spreadsheet anyway.

let checkout = Feature(
    id: "checkout",
    name: "Checkout flow",
    nativeBuildDays: 40,       // engineer-days to build once, natively
    divergence: 0.25,          // 0...1 fraction that genuinely differs per platform
    parityCriticality: 0.95,   // 0...1 cost of silent drift between platforms
    changesPerYear: 18
)

The model then prices both strategies at an agent-assist level: one scalar in 0...1 for how much of your authoring an agent really does, review rework included.

The asymmetry is the whole argument, so it is stated in the type rather than buried:

public func nativeCost(for feature: Feature, assist: Double) -> CostBreakdown {
    let author = model.authoringMultiplier(assist: assist)   // shrinks with assist
    let port = model.portFactor(assist: assist)              // collapses with assist
    let base = feature.nativeBuildDays

    let build = base * author * (1 + port)

    let ongoingAuthoring = feature.changesPerYear
        * model.changeAuthoringCost * author * (1 + port) * model.horizonYears

    // The parity tax. No agent discount: this is verification, not authoring.
    let ongoingUndiscounted = feature.changesPerYear
        * model.parityCostPerChange * feature.parityCriticality * model.horizonYears

    return CostBreakdown(build: build,
                         ongoingAuthoring: ongoingAuthoring,
                         ongoingUndiscounted: ongoingUndiscounted)
}

The shared strategy carries an undiscounted term too — release-train alignment, two teams agreeing on one API — because a model where only one side pays a fixed cost would be rigged from the start.

Eight of twelve never flip

I ran a twelve-feature catalog shaped like a consumer shopping app: checkout, cart, search, product detail, auth, pricing rules, the usual.

Four features cross over somewhere in the range. Eight never do, at any assist level between 0% and 100%. Those eight are 72% of the shared-layer budget.

The order also surprises. Nobody plans a migration this way: the largest feature in the catalog, the 40-day checkout flow, never flips. The first to flip is the scan-to-cart camera — fourth largest, and 90% divergent, which is a polite way of saying it was barely shared code to begin with.

Build size scales both strategies, so it largely cancels. The parity tax scales with churn times blast radius — an independent axis. Teams rank the port backlog by size because size is the number they can see.

Scan-to-cart camera 28 d 0.90 1.25 flips at 10%
Onboarding 14 d 0.70 0.8 flips at 48%
Settings 10 d 0.45 0.45 flips at 66%
Product detail page 30 d 0.55 5.6 flips at 92%
Checkout flow 40 d 0.25 17.1 never
Pricing and tax rules 24 d 0.05 16.0 never

The proof that it is the parity term

A model that only produces a ranking is an opinion with extra steps. So I deleted one term and re-ran it.

Set parityCostPerChange to zero — pretend verification really did get as cheap as authoring — and all twelve features flip, checkout included, crossing over at 75% assist.

One term, holding eight of twelve decisions on its own. The model has two terms agent assistance doesn't touch — the shared layer pays a fixed coordination cost per change too — but on the checkout flow this one is more than twice the size of it.

Measured on the checkout flow, moving from 0% to 100% assist: the build and authoring terms fall 62%, and the parity term falls 0%. As a share of the native bill it goes from 15.1% to 32.2% — not because it grew, but because everything around it shrank.

Agent assistance is a discount on authoring. Parity is not authoring. It is the check that two authors agreed, and nobody has made that cheaper.

What this is actually worth on Monday

Shopify's migration looks correct for Shopify — a consumer app where the UI is the product, where 50% off Android cold start and a 10× cut in crashing sessions are worth real money, and where the React Native New Architecture migration was coming due anyway. The model doesn't dispute that. What it disputes is the rule people are extracting from it.

Three things I would do before approving a port:

Price the parity term explicitly, per feature. Not "we'll be disciplined." A number, in engineer-days per change, times how often that feature changes. If you cannot produce that number, you are not ready to have the meeting.

Rank the backlog by divergence. Size is the number you can see; divergence is the one that decides. The features that leave your shared layer cheaply are the ones already full of platform-specific escape hatches — they were never really shared.

Budget the verification tooling up front. Shopify built a comparison harness for the one-time version of this question. The permanent version needs one too, and it is not free just because an agent writes the diff.

The model is a runnable Swift package — library, tests, and an Xcode project with a live assist slider, meant to be dragged until your own features leave the shared layer: shared-layer-repricer-article-demo. Swap in your own catalog; the defaults are estimates and they are meant to be argued with.

If "eight of twelve never flip" is a number you'd want in front of whoever is writing your migration business case, a clap is what gets it there — you can leave up to 50.

I want to be argued with on one input: what would you set parityCostPerChange to for your own checkout — engineer-days per change to confirm iOS and Android still behave identically? If your honest answer is under half a day, tell me what tooling gets you there, because that number decides everything else.
